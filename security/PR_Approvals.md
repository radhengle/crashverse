## PR #3: details

**Blockers**
1. **API/version mismatch, so encryption silently never runs.** Assets/Plugins/Android/CrashverseSecurePrefs.androidlib/build.gradle:8 pins `androidx.security:security-crypto:1.0.0`. Assets/_Project/Scripts/Core/InstallId.cs:37-43 uses `MasterKey$Builder`, `MasterKey$KeyScheme` and `EncryptedSharedPreferences.create(Context, String, MasterKey, …)`, but those APIs only exist from **1.1.0**. Version 1.0.0 has only `MasterKeys.getOrCreate(spec)` and `create(String, String alias, Context, …)`. On a device this throws, InstallId.cs:20 catches the error, and the ID falls back to **plaintext PlayerPrefs** (InstallId.cs:24-25) with only a warning. The test suite can't catch this because Android code doesn't run in the Editor or CI.
2. **Deprecated library.** Google deprecated all of androidx.security:security-crypto in 1.1.0-alpha07 (2025), and it gets no further fixes. Known issues:
   - `AEADBadTagException`, `KeyStoreException` and `InvalidProtocolBufferException` crashes when the prefs file and its Tink keyset outlive or mismatch the Keystore key. This happens after backup/restore, device transfer, some OEM Keystore bugs, and lock-screen changes on some devices.
   - Slow first `create()` (Tink init) on the main thread.
   - Larger binary from the bundled Tink dependency.
3. **Account-deletion wipe is incomplete.** `InstallId.Reset()` (InstallId.cs:30) clears only PlayerPrefs, not the secure-prefs entry, and nothing calls it (git grep finds no callers). The install ID, and so the ageToken binding, survives an A4 account deletion.

**Conditions**
- **Backup/restore:** PR #3's own manifest (Assets/Plugins/Android/AndroidManifest.xml) doesn't set allowBackup, and the androidlib manifest is empty. Safe behaviour depends on **#21 merging first** (allowBackup=false plus dataExtractionRules excluding all domains). If #21's rules are ever narrowed, explicitly exclude `sharedpref/crashverse_secure_prefs.xml` and the Tink keyset prefs from both `<cloud-backup>` and `<device-transfer>`, and from `fullBackupContent` on API ≤30. Otherwise a restored file meets a missing Keystore key and crashes or produces a new ID.
- **StrongBox:** not requested. 1.0.0 has no StrongBox option. In 1.1.x, `setRequestStrongBoxBacked` is slow, missing on many devices and needs a fallback. A TEE-backed key is enough for this threat model.
- **Fallback policy:** don't fall back to plaintext without notice. If the Keystore fails, regenerate the ID and log a non-PII metric, so the server just sees a new install.
- Minor: dispose the AndroidJavaObjects created at InstallId.cs:39-43 (scheme, kEnc, vEnc, master, prefs), and move the first call off the main thread.

**Recommended alternative**
- The install ID is a random, non-secret UUID, so encryption adds little. Store it as a plain file in `Context.getNoBackupFilesDir()`. That location is never backed up or transferred, whatever the manifest says. Drop the dependency.
- For real secrets (e.g. a refresh token), use a **plain Android Keystore AES-256-GCM key**:
  - Generate it with `KeyGenParameterSpec` (PURPOSE_ENCRYPT|DECRYPT, BLOCK_MODE_GCM, ENCRYPTION_PADDING_NONE, 256-bit, non-exportable, `setUserAuthenticationRequired(false)`). Try StrongBox first and fall back to TEE.
  - Store the 12-byte IV plus the ciphertext in noBackupFilesDir.
  - On `KeyPermanentlyInvalidatedException`, `AEADBadTagException` or a missing key: delete everything, regenerate and re-authenticate.
  - Alternatively, use Jetpack DataStore with Tink's `AndroidKeysetManager`.
